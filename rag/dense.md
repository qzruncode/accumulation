# Dense：基于语义向量的检索

## 一句话理解

Dense 检索（稠密向量检索）先用 Embedding 模型把文本变成一串数字，再比较问题和文本向量是否接近。它试图按“意思像不像”找内容，不只依赖原文是否出现相同关键词。

它不是某一个固定算法的名字，而是一类检索方法：模型负责把文本编码成向量，向量检索系统负责快速找出最接近的向量。

## 用一个比喻理解

想象每段文字都被放到一张很复杂的“语义地图”上：意思相近的文字通常离得近，意思差别大的文字通常离得远。用户的问题也会被放到同一张地图上，系统就去找附近的文档片段。

例如，问题是“怎么把程序发布到线上”，文档写的是“应用部署流程”。两边没有完全相同的关键词，但好的 Embedding 模型可能会把它们放得比较近，因此仍有机会搜到。

向量实际是模型生成的一长串数字，例如 `[0.12, -0.31, ...]`。这些数字通常不能逐个解释成某个具体词；它们整体的位置才用于比较语义相似度。

## 在 RAG 中怎么工作

Dense 检索通常分成“入库”和“查询”两段：

```text
入库：文档 → 切成片段 → Embedding 模型生成向量 → 保存向量和原文/页码等信息

查询：用户问题 → 同一个兼容的 Embedding 空间 → 生成问题向量
     → 找最接近的文档片段 → 返回片段和来源 → 提供给模型回答
```

关键点是，文档片段和用户问题必须能在兼容的向量空间里比较。很多检索模型支持针对“查询”和“文档”使用不同的编码提示或编码入口；应遵循具体模型的用法，而不是假设两边总要用完全相同的调用方式。[Sentence Transformers 的语义检索说明](https://sbert.net/examples/sentence_transformer/applications/semantic-search/)

文档向量一般在入库时生成一次并保存。每次搜索只需要把新问题编码，再到向量库中查近邻。向量库还会保存文档 ID、知识库 ID、页码等元数据，以便过滤范围、展示原文和生成引用；这些元数据本身不是向量。

## “稠密”是什么意思

“稠密”描述的是向量的形态：向量有固定数量的维度，而且通常大多数维度都有非零数值。Dense 向量的维度数由模型决定，例如某个模型可能输出 768 维，另一个模型可能输出 1024 维。

这和 BM25 的稀疏表示不同：稀疏表示通常只有少数词项对应的位置有值，很多位置是零；Dense 向量则把文本整体编码到一组连续数值中。稠密向量更适合表达语义相似性，但不像 BM25 那样容易直接看出具体命中了哪个词。

维度数不是质量分数。不同模型生成的向量即使维度相同，也不代表可以混在一起比较；模型、版本或编码方式变化后，通常需要重新生成文档向量。

## 系统怎么判断“接近”

向量检索系统会计算查询向量与每个文档向量的相似度或距离，并返回最接近的前 `K` 个结果。常见度量包括：

- **余弦相似度（Cosine）**：看两个向量方向是否相近；文本语义检索中很常见。
- **点积（Dot product）**：把对应维度相乘后求和；向量长度也可能影响结果。若向量都已归一化为单位长度，点积的排序与余弦相似度相同。
- **欧氏距离（Euclidean）**：看两个向量在空间中的直线距离，距离越小通常越近。

应该使用 Embedding 模型推荐的度量方式，并确保向量库的配置与之相符；不能仅凭某个度量听起来更直观就随意切换。[Qdrant 距离度量说明](https://qdrant.tech/documentation/search/)

向量库返回的相似度分数也不是“答案正确的概率”。搜索通常会尽量返回前 `K` 个近邻；即使所有候选都不相关，仍可能有一个排在第一。因此需要结合业务数据校准阈值，并允许系统在没有足够证据时不作答。

## Dense 检索的优势与边界

**适合：**

- 用户用自己的话提问，和文档的措辞不完全相同；
- 同义表达、简称或一定程度的改写；
- 希望按语义找相关段落，而非只做原词匹配。

**局限：**

- 对罕见产品型号、精确编号、股票代码等原样词项，不一定比关键词检索可靠；
- 模型不熟悉的专业领域、过长或主题混杂的片段，可能被编码得不够准确；
- 模型可能把“主题相关”误当成“能回答问题”，近邻不等于证据充分；
- 文档与查询使用了不兼容的模型、版本、维度或编码提示时，检索结果会失效或明显变差。

Dense 检索的表现取决于 Embedding 模型、分块方式、查询表达和相似度配置。切片太大可能混入多个主题，切片太小又可能丢掉回答问题所需的上下文。

## 和 BM25 怎么配合

| 检索方式 | 更擅长 | 常见漏项 |
| --- | --- | --- |
| BM25 | 原文关键词、专有名词、型号和编号 | 同义改写、意思相近但用词不同的内容 |
| Dense | 语义相近、换一种说法的问题 | 精确实体、罕见术语和原文细节 |

两种检索可以并行召回，再合并候选；需要时再用 Reranker 对较小的候选集合精排。Dense/BM25 负责“找候选”，Reranker 负责“候选里谁更相关”，它们不应混为同一步。[Dense Passage Retrieval 论文](https://aclanthology.org/2020.emnlp-main.550/)

```text
文档片段 ──┬── Dense 向量检索 ──┐
          └── BM25 关键词检索 ─┴── 合并候选 ── Reranker（可选）── 提供证据给模型
```

## 工程实践与排查

1. **固定模型和向量配置**：记录 Embedding 模型及版本、向量维度、查询/文档编码方式和距离度量。
2. **模型变更时重建索引**：不要把新模型的查询向量拿去和旧模型生成的文档向量混搜；维度相同也不意味着向量空间相同。
3. **检查过滤条件**：知识库、文档状态等过滤范围应在检索时生效，避免召回范围越界。
4. **看召回证据而不只看最终回答**：记录问题、命中的片段、分数、页码和模型配置，定位问题究竟在编码、召回还是后续生成。
5. **用代表性问题验收**：同时测试同义改写、精确编号、专业术语、文档中没有答案的问题；观察 Recall@K、MRR 等检索指标和引用是否准确。
6. **按模型建议批量编码**：入库文档可批量生成向量，需处理服务超时、限流和重试；失败的批次不能被误标为索引完成。
